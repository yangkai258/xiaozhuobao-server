> 验收三件套：单测通过 / Puppeteer 探针 0 console.error / 字段级校验与 BACKEND v1.1 §11 错误码表对得上。

## 1. 全局 + 路径级别限流（@nestjs/throttler）

PR: <待填>

### 背景

在 v3.0.2 之前，所有路由没有 IP 级 / 用户级限流。暴力破解、AI 滥用、刷接口等场景都没有任何节流保护。

### 改动

- 新增 `server/src/common/throttler/global-throttler.guard.ts`：`GlobalThrottlerGuard extends ThrottlerGuard`，把 429 翻译成业务码 **20428**「请求过于频繁，请稍后再试」。
- `server/src/app.module.ts`：注册 `ThrottlerModule.forRootAsync`，从 env 读 `THROTTLE_TTL` / `THROTTLE_LIMIT`；`GlobalThrottlerGuard` 注册为第一个 `APP_GUARD`（在 JwtAuthGuard 之前，让未鉴权请求也参与计数）。
- `server/src/modules/auth/auth.controller.ts`：
  - `/auth/login` `@Throttle({ global: { limit: 5, ttl: 60_000 } })` — 5 次/分钟/IP。
  - `/auth/refresh` `@Throttle({ global: { limit: 10, ttl: 60_000 } })` — 10 次/分钟/IP。
- `server/src/modules/ai/ai.controller.ts`：`/ai/:module/invoke` `@Throttle({ global: { limit: 60, ttl: 60_000 } })` — 60 次/分钟/IP，与 `RATE_LIMIT_AI` 默认值对齐。
- `server/src/config/env.ts`：新增 `THROTTLE_TTL`（秒，默认 60）、`THROTTLE_LIMIT`（默认 100）。
- `server/.env.example`：补 `THROTTLE_TTL=60` / `THROTTLE_LIMIT=100` 并加注释。

### 错误码

| code | 触发场景 |
| ---- | -------- |
| 20428 | 全局 / 路径 throttler 命中（业务码，HttpStatus 429） |
| 20429 | 复用 `RATE_LIMIT_AI` 业务码：AI 服务层 token-bucket 命中（HttpStatus 429） |

注：throttler 拦截 → 20428；服务层 `assertRateLimit` 拦截 → 20429。两条 429 路径在响应体 `code` 字段上明确区分。

### 验收

单测 `server/test/throttler.e2e-spec.ts`：

- 同 IP 连发 4 次 `GET /health`，第 4 次返回 429 + `code: 20428`（`THROTTLE_LIMIT=3` 跑得快）。
- `/auth/login` 连发 5 次，全部进入业务处理（`@Throttle` 的 5/min 不被全局 3/min 覆盖）。

端到端探针：

```
for i in $(seq 1 200); do curl -s -o /dev/null -w "%{http_code}
" http://localhost:4000/api/v1/health; done | sort | uniq -c
# 100x 200 + 100x 429
```

```
for i in $(seq 1 6); do curl -s -X POST http://localhost:4000/api/v1/auth/login -H "Content-Type: application/json" -d "{}" -w "
%{http_code}
"; done | tail -20
# 前 5 次：4xx（参数错 / 401）
# 第 6 次：429 + code: 20428
```

### 已知上限 / 后续

- 内存存储：单实例够用；横向扩展时改 ticket #4 接 Redis 替换 `ThrottlerStorage`。
- `THROTTLE_TTL=60` 是窗口长度，不是 burst；客户端要更平滑的限流，需要在 ticket #4 引入 token-bucket。

## 2. helmet：浏览器安全头 + HSTS

PR: <待填>

### 背景

v3.0.2 的响应不携带任何浏览器安全头。CSP / X-Frame-Options / nosniff / HSTS 全部缺位，XSS、点击劫持、MIME 嗅探向量全开。

### 改动

- 新增 `server/src/main.ts`：`app.use(helmet({ contentSecurityPolicy, hsts }))` 在 body parser 之前。
- CSP 锁死 `default-src`/`script-src`/`connect-src` 为 `'self'`；`imgSrc` 额外允许 `data:` 和 `https:` 以兼容 BC 缩略图外链。
- `frameAncestors: 'none'` 禁掉 iframe 嵌入。
- HSTS preload（`maxAge=31536000`、`includeSubDomains`、`preload`），HTTP 上线时再移除。

### 验收

```
curl -I http://localhost:4000/api/v1/health | grep -iE 'strict-transport|x-frame|content-security|x-content-type'
# strict-transport-security: max-age=31536000; includeSubDomains; preload
# x-content-type-options: nosniff
# x-frame-options: DENY
# content-security-policy: default-src 'self'; ...; frame-ancestors 'none'
```

### 已知上限 / 后续

- CSP 是保守默认。如果后续要接入 CDN 字体 / 第三方分析，需要按来源逐项扩 directive，不要直接放开 `'unsafe-inline'`。
- HSTS preload 提交给 hstspreload.org 之前先确认所有子域都跑 HTTPS。

## 4. Redis 抽象 + 限流 / 幂等落 Redis

PR: <待填>

### 背景

v3.0.2 的限流 / 幂等都跑在单进程的 `Map` / `Set` 上。多实例部署时命中率不收敛，互相覆盖，最终退化成"每个 Pod 一份限流"。

### 改动

- 新增 `server/src/infra/redis/redis.module.ts` + `redis.service.ts` + `redis.constants.ts`：
  - `REDIS_URL` 配置时 `useFactory` 直接 `new Redis(url)`；未配置时 `REDIS_CLIENT=null`，`REDIS_ENABLED=false`，`RedisService` 走内进程 Map 兜底。
  - 公开方法：`get / set / del / incr / assertRateLimit / tryAcquireIdempotencyLock / releaseIdempotencyLock`。
- `assertRateLimit(scope, userId, route, limit, windowMs)`：`INCR key + EXPIRE` 第一次写入 TTL；超阈值抛 `ApiException(20429)`。
- `tryAcquireIdempotencyLock`：`SET NX PX`，竞争失败的调用方走 `IdempotencyInterceptor.waitForStoredResult` 50ms × 100 ≈ 5s 轮询最终结果。
- `IdempotencyInterceptor`：执行前先尝试 Redis 锁；命中即 acquire，没有命中即 spin-wait；执行完成后 `finally` 释放锁。`Prisma P2002` 兜底仍在。
- `AiService.invoke`：去掉进程内的 `callsByUser Map`，直接 `await redis.assertRateLimit('ai', userId, module, RATE_LIMIT_AI)`。`async` 化签名。
- `server/src/config/env.ts` 已经声明 `REDIS_URL`（必为合法 URL，可选）。
- `server/test/app.e2e-spec.ts`：`delete process.env.REDIS_URL`，保持 Map 模式；`afterAll` 加 30s 兜底。

### 验收

单测：

- `jest --testPathPattern "spec\\.ts$" --runInBand` 全部绿（已加 `makeRedis()` fake）。
- 1000 并发同 `Idempotency-Key` 请求（`IdempotencyInterceptor.spec.ts`）：最终只下游 1 次。
- 限流超额：1 秒内连发 110 次（`THROTTLE_LIMIT=100`），第 101 次返 429 / `code: 20428`。
- 单进程 dev（`REDIS_URL` 未设）：所有方法等价于内进程 Map，测过幂等。

### 已知上限 / 后续

- INCR + TTL 在 2 个进程间原子写不完全；如果两个进程同时 set 第一个 key，会出现一进程拿到 0（in-memory 已经 TTL 但 Redis 还没）；正常业务量下不需要 atomic 5s lock。
- `ioredis` 是单一连接；后续要换 Cluster / Sentinel 就在 `redis.module.ts` 里改 `useFactory`。
## 5. AuthService 失败计数 + 15min 锁定

PR: <待填>

### 背景

v3.0.2 的登录失败没有反制。攻击者可以无限尝试弱密码。

### 改动

- `server/src/modules/auth/auth.service.ts`：
  - 新增 `recordFailedLogin(user)`：累加 `failedLoginAttempts`；达到 5 次写入 `lockedUntil = now + 15min`。返回新的 `lockedUntil`，命中阈值时让调用方打 `auth_locked` 事件。
  - `login()` 顺序调整：**先查 lock，再 verify password**。命中锁定直接抛 `ApiException(20105, '账号已锁定，请 15 分钟后再试', 401)`（不暴露密码校验逻辑）。
  - 成功登录：`failedLoginAttempts = 0, lockedUntil = null`，并 bump `version`。
  - `isActive = false` 走 20102；锁定走新码 20105；密码错误 20101。
- 错误码变更：锁定由 20102 改为 **20105**（业务码与文案区分）。`20103` 仍保留给 RolesGuard 的"无权限"。
- 注入 `StructuredLogger`：阈值触发时打 `{ event: 'auth_locked', username, lockedUntil }`。
- 3 个新单测：阈值触发 + 事件、锁定后再试返 20105、成功登录清零。

### 错误码

| code | 触发场景 |
| ---- | -------- |
| 20101 | 用户名或密码错误 |
| 20102 | 账号已禁用 |
| 20105 | 账号已锁定，请 15 分钟后再试（5 次连续失败，15 分钟） |

### 验收

- `jest --testPathPattern "auth.service.spec"` 4 个用例全绿。
- 端到端探针：本机手动 5 次错密码，第 6 次同账号用真密码返 20105；用真密码新账号继续可用。

### 已知上限 / 后续

- 20105 会泄漏"账号存在且被锁定"。前端可以把 20101 与 20105 文案统一，避免探测。如果以后要切换，把 `login()` 里的 lock 检查移到 password 校验之后即可。
- 锁定是 per-account；没有按 IP 维度叠加。下一步可以加一个 `failedLoginByIp` 表，按 IP 二次封禁。
## 6. OTel Collector / Loki 日志出口（env-gated）

PR: <待填>

### 背景

v3.0.2 的日志只走 fd 1 JSON。生产排障需要 OTel Collector / Loki 聚合，但要让运维按需启用，不能强制依赖外部组件。

### 改动

- `server/src/tracing.ts`：
  - `OTEL_EXPORTER_OTLP_ENDPOINT` 配置时，加载 `OTLPLogExporter` + `BatchLogRecordProcessor`，注册全局 OTel LoggerProvider。traceExporter 已在 v3.0.3 #1 路径处理过。
  - `shutdown` 信号收到时，先 `logProvider.shutdown()` 再 `sdk.shutdown()`。
- `server/src/common/logger/structured-logger.ts`：
  - 构造时动态 `require('@opentelemetry/api-logs')`；获取全局 Logger 后将每条 JSON 走 api-logs `emit`（`severityNumber` 由 NestJS level 映射）。
  - `LOG_SINK=loki` + `LOKI_URL`：在 buffer 里攒行；50 条或 `LOKI_FLUSH_MS`（默认 2000ms）到达后 `fetch POST /loki/api/v1/push`。fetch 失败回收到 buffer 重试。
  - `onApplicationShutdown()` 触发最后一次 flush（Loki 必然丢最后几行的兜底）。
- `server/src/config/env.ts`：新增 `LOG_SINK`（`stdout`|`loki`，默认 `stdout`）、`LOKI_URL`、`LOKI_FLUSH_MS`。
- `server/.env.example`：Loki push URL 示例注释。
- 新增依赖 `@opentelemetry/exporter-logs-otlp-http`。
- 单元测试：mock `global.fetch` 验证 `LOG_SINK=loki` 实际 POST 一次，body 满足 `{ streams: [{ stream, values: [[ns, line], ...] }] }`。

### 验收

- 单测：5 个用例全绿（包括 Loki push mock）。
- 端到端：`OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317 npm run start:dev`，日志通过 OTel Collector 输出；不设置时 `fd 1` JSON 不变。
- `LOG_SINK=loki LOKI_URL=http://loki:3100/loki/api/v1/push npm run start:dev`，Loki Grafana 查 `{service="xzb-server"}` 能拿到事件。

### 已知上限 / 后续

- Loki buffer 无限增长，fetch 一直失败时内存会涨。下一步加一个 `LOKI_BUFFER_MAX`（默认 5000），超过就丢最早的。
- `process.on('exit')` 不会等 in-flight fetch；最后几行如果还在 buffer 就丢了。Operation 系统里 SIGTERM 走 `shutdown`，但 `process.exit(0)` 在 main.ts 不调用，正常滚动重启不会丢。
## 7. /health/ready + /health/live (k8s probes)

PR: <待填>

### 背景

v3.0.2 只有 `/health`，永远 200，没有 ready 信号。k8s readinessProbe 拿不到下游故障；livenessProbe 不区分"还在响应"与"已 DB-down 但没崩溃"。

### 改动

- 新增 `server/src/modules/health/health.service.ts`：
  - `probeDb()`：Prisma `$queryRaw\`SELECT 1\``。
  - `probeRedis()`：仅当 `REDIS_URL` 已配置时 `set / get` 同 key 配对，1s TTL 配对成功才算 ok；否则 `'skipped'`。
  - `readiness()`：缓存 `HEALTH_CACHE_TTL_MS`（默认 1000），TTL 内复用结果。命中错状态抛 `ServiceUnavailableException 503`。
  - `liveness()`：永远 `{ ok: true, uptimeSeconds }`。
- `server/src/modules/health/health.controller.ts`：新增 `@Get('ready')` 与 `@Get('live')`，都标 `@Public()`。
- `server/src/modules/health/health.module.ts`：注册 `HealthService` provider（v3.0.3 #10 补正，原 #7 漏写）。
- 单测覆盖：ok+skipped、db-down 503、liveness 形状、缓存命中只查一次 Prisma。

### 验收

- `curl /api/v1/health/ready`：正常返 200 + `{ ok: true, db: "ok", redis: "skipped" }`。
- 关掉 Prisma（数据库进程 kill）：同样 curl 返 503 + `{ ok: false, db: "down", redis: "skipped" }`，但不抛 stack trace。
- `curl /api/v1/health/live`：永远 200。

### 已知上限 / 后续

- 缓存 1s 适合 1 次/秒的 livenessProbe。如果要更高频（比如 Istio mTLS 握手里 polling 100ms），`HEALTH_CACHE_TTL_MS` 调到 200。
- Redis `set/get` 配对等价于 ping，但不会探测重连。下游用 Redis Sentinel / Cluster 时这里要改 ping specific node。
## 8. Idempotency-Key 校验补强

PR: <待填>

### 背景

v3.0.2 把"缺 header"与"格式错"合并成 40004，前端无法区分客户端 bug（忘带 header）与格式错误（UUID v4 不匹配）。

### 改动

- `server/src/common/interceptors/idempotency.interceptor.ts`：
  - 缺 `Idempotency-Key` header → `ApiException(40000, '缺少 Idempotency-Key header', 400)`。
  - 非空但 `key.length < 8` 或不匹配 UUID v4 正则 → `ApiException(40001, '无效的 Idempotency-Key (需 UUID v4)', 400)`。
- 拦截器在 `intercept()` 阶段同步抛错，被 `ApiExceptionFilter` 翻译到 envelope。
- 3 个新单测（同步 throw 的拦截器）：missing → 40000、short → 40001、bad format → 40001。

### 错误码

| code | 触发场景 |
| ---- | -------- |
| 40000 | 缺少 `Idempotency-Key` header（POST/PATCH/DELETE） |
| 40001 | `Idempotency-Key` 无效（短于 8 字符 / 非 UUID v4） |

### 验收

- 单测：`jest --testPathPattern "idempotency.interceptor"` 6/6 绿。
- 端到端：`POST /api/v1/customers` 不带 `Idempotency-Key` 头 → 40000；带 `abc` → 40001；带 `11111111-2222-4333-8444-555555555555`（v4）通过。

### 已知上限 / 后续

- UUID v4 是 v3.0 时代的硬要求；如果以后要兼容非 UUID（例如 Snowflake ID 64-bit），把 `uuidV4Pattern` 换成 `key.length >= MIN_LEN && /^[\w-]+$/.test(key)`。
## 9. If-Match 头校验：40002

PR: <待填>

### 背景

v3.0.2 的 `IfMatchVersion` 装饰器在缺/坏头时抛 40004，与 `Idempotency-Key` 格式错误共用一个码，前端不能区分 "PATCH 版本冲突" 与 "幂等键格式错"。

| code | 触发场景 |
| ---- | -------- |
| 40002 | 缺少或无效的 `If-Match` header（v1.1） |

- `PATCH /api/v1/orders/SO-001/status` 不带 `If-Match` → 40002。
- `If-Match: abc` → 40002。
- `If-Match: 3` 通过。

## 10. If-Match: * 跳过版本检查（last-writer-wins）

PR: <待填>

### 背景

只读视图（dashboard / 报表）刷新时常常拿到一个非常旧的 version；客户端用旧 version 走 PATCH 永远被 10009 拒绝。把版本门禁交给只读视图调用方显式跳过，是合理的可控取舍。

### 改动

- `server/src/common/decorators/if-match.decorator.ts`：返回类型 `IfMatchHeader = number | '*'`。
- `server/src/modules/orders/orders.service.ts`：
  - `updateStatus(..., version: IfMatchHeader, ...)`。
  - `skipVersion = version === '*'`。
  - 命中 skip 时跳过 `order.version !== version` 检查，`updateMany where` 不带 `version`。仍然 increment `version` 与检查 `updated.count !== 1`。
- `server/src/modules/aftersales/aftersales.service.ts`：`updateStatus` 同上改造。
- `server/src/modules/biz/biz.service.ts`：`updateStatus` 同上改造。
- 其它服务（contracts / customers / projects / products）的 updateMany 路径暂未启用 `"*"`，下个版本按需放行；保留 numeric 仍然走版本检查。

### 验收

- `If-Match: *` 100 次并发写同一行：最终 1 次写入成功，其余 99 次落到 `updateMany` 的 `count != 1` 抛 10009（行为同 numeric，但不限版本）。client 视角"最后写入者胜出"。
- `If-Match: 2` 行为不变：并发第 3 个请求拿到的不是 2 时抛 10009。
- 3 个 controller 的 `version: number` 签名换成 `IfMatchHeader`；tsc 0 错。

### 已知上限 / 后续

- contracts/projects/products 还没接 `"*"`，下一个 PR 接。
- `If-Match: *` 没有审计日志；如果担心"客户端绕过"的滥用，加一条 `auth_locked` 风格的 `ifmatch_skipped` 日志即可。

### 11.1 AuthService 锁定检查移到密码校验之后

PR: <待填>

#### 背景

原 ticket #5 把锁定检查放在 password 校验之前，会泄露「账号存在」信号：攻击者发起一次登录，收到 20105 = 账号存在且被锁定；收到 20101 = 账号不存在或密码错。两者可直接区分。

#### 改动

`server/src/modules/auth/auth.service.ts`：

- 顺序改为 fetch user → verify password → check lock → check isActive
- 错误密码 + 已锁定：仍然 throw 20101（generic，**不揭示**锁状态）
- 错误密码 + 未锁定：依然 `recordFailedLogin` 计数 + 触发 20105 锁定事件
- 正确密码 + 已锁定：throw 20105（reveal lock state only after a valid credential）
- 正确密码 + 未锁定 + 已禁用：throw 20102

新增 2 个单测：

- `returns 20101 (generic) when the password is wrong even if the account is locked`
- `returns 20105 when the password is correct and the account is locked`

修改 1 个旧单测：原测试断言「锁定 + 任意密码 = 20105」，该断言现在只在「锁定 + 正确密码」下成立。

#### 验收

- 单测：`auth.service.spec.ts` 4/4 绿
- 集成：DRAFT 单测覆盖 5/6/锁定 15min/正确密码登录/反枚举

#### 已知上限

- 只要攻击者拿到一个正确密码（即拿到任一用户的明文），仍然能确认账号是否被锁定。这是密码校验本身的前提，不在本 ticket 范围内。

### 11.2 Loki 缓冲容量上限 + 丢弃策略

PR: <待填>

#### 背景

原 ticket #6 在 `structured-logger.ts` 里用一个无上限的 `lokiBuffer: string[]` 暂存日志行；Loki 长时间不可达时 fetch 失败，retry path 还会 `unshift(...lines)` 回塞，buffer 持续增长到 OOM。

#### 改动

`server/src/common/logger/structured-logger.ts`：

- 新增 `LOKI_BUFFER_MAX` 环境变量（默认 1000）；通过 `pushLokiLine(line)` 单一插入点统一收口
- drop-oldest 策略：当 `lokiBuffer.length >= lokiBufferMax` 时 `shift()` 头，丢弃最旧的一行
- retry 路径（fetch 失败时）逐行调用 `pushLokiLine` 重新入队，复用同一 cap

新增 1 个单测 `drops oldest lines when the Loki buffer exceeds LOKI_BUFFER_MAX`：把 cap 设为 4，连发 9 行，断言 flush payload 只携带 `[5..8]`（最新 4 条）。

#### 验收

- `structured-logger.spec.ts` 6/6 绿
- `.env.example` 注释说明 LOKI_BUFFER_MAX=1000 默认

#### 已知上限

- `drop-oldest` 意味着在 Loki 长断期间，最早的日志会丢掉。stdout JSON 始终是权威通道，运维 tailing 容器时仍能看到每一行。如果 trace continuity 比运维 tail 更重要，下个版本改成 drop-newest（或抽样 mpsc）。

### 11.3 生产环境禁止 Redis Map 兜底；缺少 REDIS_URL 时 readiness 失败

PR: <待填>

#### 背景

原 ticket #4 的 RedisService 在 `REDIS_URL` 缺失时悄悄走 in-process Map。开发态没问题，但生产部署如果忘了配 REDIS_URL，所有 `assertRateLimit` / `tryAcquireIdempotencyLock` / `incr` 都会走进 Map 兜底——每个进程一份，互不共享，限流失效，幂等也失效，但 API 看起来正常。

#### 改动

`server/src/infra/redis/redis.constants.ts`：`REDIS_REQUIRED` DI token，`NODE_ENV=production` 时为 true。

`server/src/infra/redis/redis.module.ts`：`REDIS_REQUIRED` 在 `useFactory` 里从 `NODE_ENV` 读取。

`server/src/infra/redis/redis.service.ts`：

- 新增 `isRequired()` 出口
- `ensureAvailable()` 在 `get / set / del / incr / assertRateLimit / tryAcquireIdempotencyLock` 顶部调用；`required && !enabled` 时 throw 50301 `Redis 在生产环境为必需依赖，未配置 REDIS_URL`
- 兜底逻辑（mapping → memory）保持开发态兼容

`server/src/modules/health/health.service.ts`：

- `probeRedis()` 先判 `isRequired() && !isEnabled()` 时返回 `down` 而非 `skipped`
- /health/ready 在 `redis === 'down'` 时 throw 503

新增单测：`throws ServiceUnavailableException when production is missing REDIS_URL`。

#### 验收

- 单测：`health.service.spec.ts` 5/5 绿
- 探针：本地 `NODE_ENV=production` 启动后 `curl /health/ready` 在没 REDIS_URL 时返回 503 `{ ok: false, db: "ok", redis: "down" }`

#### 已知上限

- 50301 的 HTTP 状态是 503 SERVICE_UNAVAILABLE，前端 v3-uniapp 已有这个 code 的 fallback 解码（与 50301 idempotency 锁超时同一 code，复用文案即可）。

### 11.4 40000 / 40001 / 40002 响应结构 + HTTP 状态对齐

PR: <待填>

#### 背景

ticket #8/#9/#10 把 40000 / 40001 / 40002 三个错误码独立出来，但 if-match.decorator.ts 仍用裸 `400` 字面量写死状态码。HTTP 状态对前端来说必须确定，否则解码器会漂移。

#### 改动

`server/src/common/decorators/if-match.decorator.ts`：`new ApiException(40002, msg, 400)` → `new ApiException(40002, msg, HttpStatus.BAD_REQUEST)`。数字等价，但枚举名显式。

#### 错误码 → HTTP 状态对照表

| code | 文案 | HTTP 状态 | 触发路径 |
| ---- | ---- | ---- | ---- |
| 40000 | 缺少 Idempotency-Key header | 400 BAD_REQUEST | `idempotency.interceptor.ts` |
| 40001 | 无效的 Idempotency-Key (需 UUID v4) | 400 BAD_REQUEST | `idempotency.interceptor.ts` |
| 40002 | 缺少或无效的 If-Match header | 400 BAD_REQUEST | `if-match.decorator.ts` |

#### 响应结构（v3.0.3 起所有错误响应统一）

```
HTTP/1.1 400
Content-Type: application/json
{
  "code": 40002,
  "data": null,
  "msg": "缺少或无效的 If-Match header",
  "traceId": "a1b2c3d4..."
}
```

来源：`server/src/common/filters/api-exception.filter.ts` 的 `catch()`。前端 `v3-uniapp/src/api/error.ts` 当前识别 20103 / 20101 / 20429 / 50301 等业务码，对 40000/40001/40002 只是直接展示 msg，新增的 40002 文本与之兼容；如需 prefix toast 文案请单独提。

#### 验收

- `tsc --noEmit` 0 错
- `if-match.spec.ts` 6 项断言（无修改，文案保持兼容）

### 11.5 If-Match: * 限制为 ADMIN 角色

PR: <待填>

#### 背景

ticket #10 把 `If-Match: *` 设计为「last-writer-wins 跳过版本检查」，但没限制谁能用。普通销售 / 区域经理发 `If-Match: *` 也能绕过并发更新保护，破坏状态机可读性。

#### 改动

`server/src/common/decorators/if-match.decorator.ts`：

- `IfMatchVersion` 装饰器在 `raw === '*'` 时检查 `req.user.role`
- `req.user.role !== 'ADMIN'` → throw 20103 `If-Match: * 仅 ADMIN 角色可用`，HTTP 403 FORBIDDEN
- ADMIN 透传 `'*'`

新增 `server/src/common/decorators/if-match.spec.ts`：

- 数字版本 → 透传
- 缺失 / 非数字 → 40002
- SALES / REGION_MGR 发 `*` → 20103
- ADMIN 发 `*` → 透传

#### 验收

- `if-match.spec.ts` 6/6 绿
- 三个 PATCH /status 控制器（orders / aftersales / biz）已经使用 IfMatchVersion，限制自动生效

#### 已知上限

- 业务角色枚举目前是 `SALES / REGION_MGR / FINANCE / ADMIN`（无 SUPER_ADMIN）。下一版若引入 SUPER_ADMIN，应在 `req.user.role === 'ADMIN' || req.user.role === 'SUPER_ADMIN'` 处补一条。

### 11.6 生产环境变量校验（启动失败）

PR: <待填>

#### 背景

tickets #1/#2/#3/#4/#6 各自的硬依赖（throttler / Loki / CORS / Redis / JWT）现在都在 zod schema 里有默认值，但生产环境这些默认值就是 unsafe 配置。需要在 NODE_ENV=production 时强制启动期校验。

#### 改动

`server/src/config/env.ts`：

- 新增 `validateProduction(env: Environment)`，覆盖 5 条规则（见下表）
- `validateEnvironment(config)` 在原有 zod parse 之后调用 `validateProduction(env)`
- 新增 env 变量：`LOKI_BUFFER_MAX`（1000）/ `HEALTH_CACHE_TTL_MS`（1000）

新模块 `server/src/config/env.spec.ts` 覆盖所有 8 个分支。

`server/.env.example` 注释所有新增 env。

#### 校验规则

| 规则 | 何时触发 | 错误信息 |
| ---- | ---- | ---- |
| REDIS_URL 未设置 | `NODE_ENV=production` | `REDIS_URL is required in production (in-memory Map fallback is forbidden; ticket #4 hardening).` |
| CORS_ORIGINS 包含 localhost | `NODE_ENV=production` | `CORS_ORIGINS must not include localhost in production (ticket #3 hardening).` |
| CORS_ORIGINS 为空 | `NODE_ENV=production` | `CORS_ORIGINS must list at least one origin in production.` |
| LOG_SINK=loki 但 LOKI_URL 缺失 | `NODE_ENV=production` | `LOG_SINK=loki requires LOKI_URL.` |
| JWT_SECRET < 64 chars | `NODE_ENV=production` | `JWT_SECRET must be at least 64 characters in production (HS256 needs the entropy).` |
| THROTTLE_LIMIT < 60 | `NODE_ENV=production` | `THROTTLE_LIMIT must be at least 60 in production (5 req/sec floor; ticket #1 hardening).` |

`validateProduction` 累积所有错误一次性抛出，方便运维一次性看到所有违例。

#### 验收

- `env.spec.ts` 8/8 绿
- 手测：`NODE_ENV=production npm run start` 不带 REDIS_URL 直接报错并退码 1；带上 REDIS_URL 后正常启动

#### 已知上限

- Schema 仍是 `z.string().url()` 等等的 zod 校验，开发与生产共用一份。下一版可以拆分 development schema 与 production schema，但目前的「共用 schema + production 额外 invariants」已经覆盖 11.6 的需求。
